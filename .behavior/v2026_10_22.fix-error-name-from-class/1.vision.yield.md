# 1.vision — helpful-errors never touches `error.name`

scope per the wish's amendment of 2026-10-22. the prior scope (`name` equals the class) is overturned; fulcrum F6 records it, and its experience catalog sits in `archive/scope=name-equals-class/`.

## the outcome world

### before

```ts
const error = new ConstraintError('quote lacks provider', { quoteUuid });
error.name;     // 'Error'
String(error);  // 'Error: ✋ ConstraintError: quote lacks provider …'
```

the behavior is already right. what is absent is a guard: one line, `this.name = new.target.name`, looks like an obvious fix for a log that reads `errorType: 'Error'`, and it was proposed (#45) and built (#46) before anyone asked who reads `name`.

### after

the runtime is unchanged — same `name`, same message, same json, same snapshots. what changes:

- `rule.forbid.error-name-override.md` forbids any route that sets or shadows `name`, and names a switch on `error.name` as a code smell
- `src/HelpfulError.name.test.ts` goes red the moment any route sets `name`
- the readme tells a consumer to use `instanceof` or `isHelpfulError`, never `name`

### the aha

the class already leads every message: `✋ ConstraintError: …`. a set `name` repeats it — `ConstraintError: ✋ ConstraintError: …` on every render — and the one reader who wanted it, a client keyed on lambda's `errorType`, had the fix on the wrong side. the producer classifies by class and writes a deliberate field (`genConstraintErrorMiddleware`), so the wire never needs `name`.

## the contract

- `error.name` reads `'Error'` for `HelpfulError`, each built-in, and any consumer subclass that does not set its own
- the library never defines `name`: no own property on an instance, no property on any class prototype, no key in `toJSON` output
- the clamp asserts all four, per class, for the base, each built-in, and one consumer subclass
- constructor inputs, message format, and json shape: unchanged

## mental model

- to a friend: *"the error already says what it is at the front of its message. `name` would say it twice. if your code needs the class, check the class."*
- terms: `name` is the js field; `errorType` is aws's copy of it; neither is how this library states a class

## evaluation

- goals: met — the invariant holds by test, and the rule records why so the question stays closed
- pros: zero runtime change; zero snapshot churn; one place to read the decision
- cons: a consumer keyed on `name` or lambda's `errorType` for an unhandled throw sees `'Error'`. that is the true label for an unhandled throw; a caller fault is the producer's to classify
- pit of success: the clamp fails at the first attempt, before review, with a pointer to the rule
